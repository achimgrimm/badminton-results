# OT Bremen Badminton – Ergebnisse

Mobile-friendly view of every badminton team of **TSV Osterholz-Tenever (OT Bremen)**, season 2026/27: next match, league table, full schedule, every Spielbericht, match previews and player statistics. Data is scraped from [nuLiga](https://brbv-badminton.liga.nu/cgi-bin/WebObjects/nuLigaBADDE.woa/wa/clubTeams?club=11473), which has no public API.

The site root is a team chooser. Each team lives in its own folder (`aktive/`, `aktive-2/`, `aktive-3/`, `jugend/`, `jugend-2/`, `schueler/`). The app remembers the last team and opens it next time; `index.html#auswahl` always shows the chooser.

## Usage

Tools are managed with [mise](https://mise.jdx.dev) (`mise.toml` pins Node 22 and the GitHub CLI):

```sh
mise install       # install Node and gh
mise run update    # test, scrape, build
mise run serve     # preview dist/
mise tasks         # list all tasks
```

Or with npm directly:

```sh
npm install
npm run scrape   # fetch nuLiga pages -> data/*.json
npm run build    # data/*.json -> dist/ (static HTML)
npm run serve    # preview dist/ locally
npm test         # parser tests against test/fixtures
```

## How it works

- `src/scrape.ts` reads the club's team list from nuLiga on every run, so new teams or a new season need no code change. For each league it fetches the table and schedule (at most 1 request/s), plus a Spielbericht only when it is new or not yet approved; leagues with two OT teams (Jugend, Jugend II) are fetched once. Each hall address is fetched once. Data lives in `data/groups/<group>/` and `data/teams/<slug>.json`.
- Youth leagues use numbered pairings (`D1-D1`, `2-2`), stored as `D1`, `E2`.
- `src/parse/*` hold the cheerio parsers for each nuLiga page type. If nuLiga changes its markup, update the matching parser and refresh the fixture in `test/fixtures/`.
- `src/render/*` render the plain HTML pages. Styling follows the OT design tokens in `src/styles.css`.
- `.github/workflows/update.yml` runs hourly and on every push to `main`. It builds the live site from `main` and a test stage from every other branch (see [Test stages](#test-stages)), each with its own tests, scrape and data cache, and deploys them together to GitHub Pages. If the live build fails, nothing is deployed and the last good deploy stays online; a failing stage only misses its folder.
- The site is an installable PWA. `src/render/pwa.ts` generates the manifest and the service worker. Pages are network-first with an offline fallback to the last cached copy. The app icons in `src/icons/` are rendered from `icon.svg`.
- Results of the selected team that are new on the device get a "Neu" badge for 24 hours (or until their Spielbericht is opened). The client script `NEW_RESULTS` in `src/render/layout.ts` keeps first-seen times in localStorage under `seen-<team slug>`; on the first visit to a team nothing is marked. Results first seen on a page load are also listed once in a pop-up (Umami event `new-results`).
- Players can answer for the own matches whether they play in ("Ich spiele" next to every unplayed match card, in the "Nächstes Spiel" box and on the Vorschau page; on the Übersicht only while no player is chosen). One button cycles through Dabei (yes), Vielleicht (maybe), Kann nicht (no) and unanswered. Yes and maybe matches get a "Dabei" or "Vielleicht" badge (yes also after the result is in), and the Spielplan filter "Meine Spiele" shows both; no counts as not marked. The Spielplan's always visible "Meine Spiele teilen" button sends the upcoming yes and maybe matches (date, time, home/away, opponent, "(vielleicht)" for maybe, Vorschau link) as plain text through the phone's share sheet (WhatsApp, Signal, …), falling back to the clipboard; with none marked it asks to mark matches first. The client script `PLAYING` in `src/render/layout.ts` keeps an object of `previewName` keys (`heim-<opponent>`/`auswaerts-<opponent>`) to `yes`/`maybe`/`no` in localStorage under `playing-<team slug>-<season>`; unanswered matches have no entry. Older versions stored a plain list of keys (all yes); `migratePlaying` in `src/playing.ts` converts it on load. Nothing leaves the device (Umami event `playing`, `state`: `yes`, `maybe`, `no` or `none`).
- Players can tell the app who they are ("Wer bist Du?" on the Spieler page, or "Das bin ich" on a player page). The list comes from nuLiga's club roster (`clubPools`, Vereinsrangliste): the team's Stammspieler and the club's reserve players of its age classes (`POOLS` in `src/config.ts`; the Rückrunde roster once nuLiga has one), plus anyone else who played for the team in a Spielbericht. The scrape stores it in `data/rosters/<slug>.json`. nuLiga has no gender field, but Aktive players come from separate "O19 Herren" and "O19 Damen" lists (`POOL_GENDER` in `src/config.ts`), so they get `gender` `m`/`f`; the mixed youth lists give none. Players not on those lists get it from the Herren or Damen game they played in a Spielbericht (`playerGenders` in `src/lineup.ts`). The Spieler list and player pages show it as "Herren"/"Damen". The chosen player is highlighted in the Spielberichte and the player list (sorted by the name as shown, first name first; the chosen player on top), and their player page says "Das bist Du". Played matches whose Spielbericht lists them count as theirs (yes), answered or not: "Dabei" badge and the Spielplan filter "Meine Spiele" (the build puts the OT lineup's person ids on each played card as `data-players`). With a player chosen, the Übersicht shows only their matches: the hero is their next yes or maybe match ("Kein Spiel markiert" with a link to the Spielplan if there is none), "Weitere Spiele" the later marked ones, and results only theirs of the last 14 days, without "Ich spiele" toggles (script `PERSONAL` in `src/render/index.ts`). The client script `ME` in `src/render/layout.ts` keeps `{ person, name }` in localStorage under `me-<team slug>-<season>`, per team. Signed out, nothing leaves the device (Umami event `me`); signed in, the pick is also the account's claim of that player (see "Player claims" below).
- "Aufstellung planen" on the Vorschau page (`lineupEditor` in `src/render/vorschau.ts`, rules and player sections in `src/lineup.ts`): anyone can pick who plays which game; the games come from the league's first Spielbericht (fallback per team label). The player lists are the players who already played for the team in a Spielbericht, then the other Stammspieler, then the reserves. Client-side `lineupIssues` checks: a player plays at most 2 games, never two singles or two doubles; Herren games need men, Damen games women, Mixed one of each (only for players whose gender is known). Herren and Damen games only offer men and women respectively, players of unknown gender are offered everywhere. There is no ranking check, since nuLiga's ranking isn't reliably up to date. Warnings never block saving. Under each game the editor shows who the opponent usually fields there (`probableOpponents` in `src/lineup.ts`, from `stats.lineup`: most played first, the rest behind "weitere"; names link to the opponent's player pages); the separate "Aufstellung des Gegners" fold only appears while no games are known. For team leads and admins signed in (permission `answers.read_all`), each player's answer for this match ("Dabei"/"Vielleicht"/"Kann nicht", no badge without an answer) is shown in the picker dialog and next to the selected players, and a selected player who said no gets a warning line (never blocks); `Online.teamAnswers` calls the function `team_answers(team, season, game_key)` (`security definer`, only approved `player_claims` map an answer to a person; `game_answers` itself stays owner-only; mapping in `src/answers.ts`, tests `test/answers.test.ts`). Publishing: team leads and admins (permission `lineup.write`) get "Veröffentlichen"/"Zurückziehen" and a status line in the editor; publishing writes the device draft to `published_lineups` (team slug, season, `previewName`, jsonb `{ discipline: [person, …] }`, publisher, time; RLS: every signed-in user reads, only `lineup.write` writes; migration `20261117000000_published_lineups.sql`; `Online.publishedLineup`/`publishLineup`/`unpublishLineup`, `parsePublished` in `src/lineup.ts` validates what is read). Every other signed-in user sees the read-only card "Aufstellung vom Mannschaftsführer" (`#published-lineup`, filled by the `LINEUP` script; their own player in bold; "Noch keine Aufstellung veröffentlicht." until then); the last fetched lineup is cached in localStorage (`<lineup key>-published`) for an offline start. Planning stays a private draft until published; a later edit shows "Dein Entwurf weicht ab". Umami `lineup` actions `publish` and `unpublish` (`ok`). In that cloud mode "Vorschlag" skips players with "no" (`blocked` in `suggestLineup`; yes, maybe and no answer stay eligible, hand-picking a "no" player is always possible); signed out or without the permission nothing changes. "Vorschlag" fills only the empty slots (Umami `lineup`, `action: "suggest"`): the build embeds `lineupHistory` (per game who played it for the team, each older Spielbericht weighted ×0.75), and the client-side `suggestLineup` (`src/lineup.ts`) takes the usual pair or player of each game first, then fills single slots by weight in that game, else in a similar game (×0.5), else any (×0.1), keeping to the rules above; a slot nobody fits stays empty. Players are picked in a dialog, not a native `<select>` (hidden, it only holds the value): Chromium opens a list of 25+ names over the field, so the click's mouse-up selected an entry at once. The client script `LINEUP` keeps `{ discipline: [person, …] }` in localStorage under `lineup-<team slug>-<season>-<previewName>`; "Aufstellung teilen" sends it as plain text through the share sheet (clipboard fallback). Nothing leaves the device (Umami event `lineup`).
- "Spiele in Deinen Kalender" (on the Spielplan, next to ".ics herunterladen") subscribes to nuLiga's `webcal:` feed. Android has no handler for `webcal:`, so there the button links to Google Calendar's "add by URL" page (`calendar.google.com/calendar/r?cid=…`) instead; the subscription stays up to date and syncs to the phone's calendar app (Umami event `calendar`, `via`: `google` or `webcal`).
- Online features (Supabase, EU/Frankfurt; issue #24): optional Google sign-in in the header menu ("Mit Google anmelden"; signed in: the chosen player (linked to the player page; else the Google name), role, claim status, "Abmelden" (also clears the chosen player on this device), "Konto löschen"; the profile name is not editable). `SUPABASE_URL` and `SUPABASE_ANON_KEY` in `src/config.ts` (the publishable key is public by design; access is enforced by row-level security); an empty URL or key sets `ONLINE` to false, and then no bundle, footer account line or request exists. `src/client/online.ts` (supabase-js, PKCE flow) is bundled by `buildOnlineBundle` in `src/build.ts` with esbuild to `online.js` (hashed URL) and exposes `window.Online` for later features. The session is stored under `storageKey("auth")`, so stages don't share the live login. Everything else works without sign-in and nothing leaves the device unless a feature says so. Schema and policies live in `supabase/migrations/`: `profiles` plus role-based access control (RBAC): `roles` (`admin`, `team_lead`, `member`; global, not per team), `permissions` (`role.manage`, `lineup.write`, `template.write`), `role_permissions` and `user_roles`. Every new account gets `member` (trigger `handle_new_user`). Policies of later tables check `public.has_permission('<permission>')`, and a feature adds its own permissions and `role_permissions` rows in its migration; `public.my_permissions()` feeds `Online.can(permission)` in the client (UI only, the server enforces it). No client can write any role table, so nobody can grant themselves a role: the first admin is made once in the SQL editor with `insert into public.user_roles (user_id, role) select id, 'admin' from auth.users where email = '<your email>';`, and later admins and team leads in the app: with `role.manage` the menu shows "Rollen verwalten" (`openRoles` in `online.ts`), a dialog listing all accounts that grants or revokes team lead and admin through the `security definer` functions `list_users_with_roles()` and `set_user_role()` (which refuse removing your own or the last admin role; Umami event `role-change`). `delete_account()` removes the user and, by cascade, their profile and roles. `.github/workflows/migrate.yml` runs `supabase db push` when `main` changes `supabase/**` (secret `SUPABASE_DB_URL`, the Session pooler connection string, because GitHub runners have no IPv6); stages never migrate, so the first migration is applied by hand with `supabase db push --remote=<Session pooler string>`. `scripts/keepalive.ts` reads one row in the hourly live build so the free project doesn't pause. The privacy policy is `datenschutz.html` (`src/render/datenschutz.ts`), linked from every footer; the sign-in sections show only when `ONLINE`. Setup: enable Google under Authentication → Providers (Google Cloud OAuth client with the project's `/auth/v1/callback` as redirect URI) and list the callback pages as redirect URLs: `https://achimgrimm.github.io/badminton-results/auth-callback.html`, `…/stage/*/auth-callback.html` and `http://localhost:3000/auth-callback.html`. Sign-in always returns to `auth-callback.html` (`src/render/auth-callback.ts`), which finishes the login and sends the visitor back to the page stored in sessionStorage (`auth-return`) or to the site root. Text columns users can write have length limits (`20261114000000_text_length_limits.sql`, `NOT VALID` so existing rows are untouched). Every page carries a Content Security Policy as a meta tag (`CSP` in `src/render/layout.ts`; GitHub Pages can't send headers): scripts only from this site and Umami, requests only to this site, Supabase and Umami; add a new external host there (`test/menu.test.ts` checks it). Scraped Google Maps links must be https (`parseCourt`), logos are fetched only from nuLiga's host and never as SVG. Umami events: `login`, `logout`, `delete-account`.
- Player claims: signed in, the "Wer bist Du?" pick of a team and season is stored on the account (`player_claims`: user, team slug, season, nuLiga person, name, status `pending`/`approved`; unique per account and team/season; only an approved claim owns a player (partial unique index), so pending claims for the same player may coexist and approving one rejects the others, see `20261115000000_claims_pending_dont_block.sql`). The ME script exposes `window.otMe` and reports picks through `window.otMeChanged`; `online.js` sends them as claims, and after sign-in `reconcile` in `src/claims.ts` decides: an approved claim wins over the device's pick, a pending one only fills an empty device, otherwise the device's pick becomes the new claim. A claim is `pending` until an admin or team lead (permission `player.link`) approves it in the menu ("Anfragen prüfen") or rejects it (the row is deleted); their own picks are approved at once, and users have no update policy, so nobody approves themselves. Pending claims already work on the device; the signed-in menu shows a check mark next to the name once it is confirmed, or "Spieler wartet auf Bestätigung" until then; signed out with a chosen player it says "Spieler nur auf diesem Gerät". Replacing an approved claim asks first, and a player that is approved for another account keeps the device-only pick. The approval dialog tells when several requests name the same player. Approvers can read the claimers' display names (policy on `profiles`) and, for pending claims only, their email addresses through the function `pending_claim_emails()` (shown under the name in the approval dialog). Umami events: `claim` (`action`: `pending`, `approved`, `automatch`, `pick`, `clear`), `claim-decision`. First sign-in without a chosen player: `confirmPlayer` in `online.ts` opens a dialog that can only be left by confirming or signing out ("Wer bist Du?"). It looks the Google name up in the team's roster, which the build embeds in every team page as JSON (`#me-roster`, from `pickablePlayers`); `matchPlayer` in `src/names.ts` accepts only a single exact match (case, accents, punctuation and name order ignored; players with the same name never match) and preselects it, otherwise nothing is preselected. The confirmed pick is sent as a normal claim, so it still needs approval. Signed in, the player can't be cleared, only replaced: "Ich bin nicht …" and toggling the player off call `window.otClearMe` (set by `online.js`), which opens the same dialog ("Neuen Spieler wählen", without the current player; cancelling changes nothing) and only a confirmed new player changes the pick and the claim. The dialog returns on every load until a player is chosen (Umami `claim` action `automatch` when the preselection was confirmed, `pick` otherwise). The device also notes the last pick it sent (`-attempt-`): if that claim has vanished from the server it was rejected and the pick is reset; if the player belonged to another account, the pick stays on this device and is not sent again.
- Local and cloud mode, answer sync (table `game_answers`: user, team slug, season, `game_key` = the `previewName`, `state` yes/maybe/no or null for a cleared answer, `updated_at`; own rows only through RLS; trigger `game_answers_keep_newer` skips an update older than the stored row). Signed out (local mode) the "Ich spiele" answers live only in localStorage (`playing-<team>-<season>`). Each change also stamps its time in `answers-at-<team>-<season>` (`{ gameKey: ms }`; a cleared answer keeps its time, so deletes sync). Signed in (cloud mode) `src/client/sync.ts` (pure logic in `src/sync.ts`, tests in `test/sync.test.ts`) keeps the device as an offline copy: per game the newer change wins, in both directions. What is pending is derived, not queued: a game whose time is later than the one stored in `<auth key>-synced-<user>-<team>-<season>`. A sync runs after sign-in, after an answer (event `ot-answers`, debounced), when the connection returns (`online`), when the tab becomes visible again and before signing out; it pulls the account's rows, merges them and re-renders (`window.otPlayingRender`), then uploads the pending changes. It fails quietly offline and retries on the next trigger. The first sign-in of an account on a device (note `<auth key>-sync-<user>`) decides once with `firstSync`: a new account takes the device's answers; an existing one takes its own when the device has none or the same; otherwise a dialog asks "Cloud oder lokal?" (account data overwrite the device, or the device's overwrite the account). Signing out keeps the answers on the device (the offer to clear local data stays); deleting the account also offers to clear them.
- Usage is counted with [Umami Cloud](https://cloud.umami.is) (cookieless, no consent banner needed). The website ID is `UMAMI_WEBSITE_ID` in `src/config.ts`; an empty ID turns tracking off. Only the live domain is counted, not local previews. Every page view is tagged `app` (installed PWA) or `browser`. Each session also carries properties (`umami.identify`, session data in the dashboard): `app` (`app`/`browser`), `team` (`yes`/`no`: a team is selected), `player` (`yes`/`no`: a player name is chosen) and `storage` (`local`, or `cloud` when signed in). They live in the `otProps` registry of the `ANALYTICS` script in `src/render/layout.ts`: a new attribute is one more entry there (a probe function returning a coarse value, no names); `otIdentify()` sends them all after the Umami script loads and whenever the team or player changes, and `online.ts` passes `storage` on every auth change (`otIdentify({ storage })`). Events: `theme`, `install-click`, `install-accepted`/`install-dismissed`, `app-installed`, `open-in-chrome`, `share`, `new-results`, `release-notes`, `menu`, `feedback-signal`, `feedback-mail`, `playing`, `share-plan`, `calendar`, `me`, `lineup`.
- The header has one menu button (`MENU` and `menuDialog` in `src/render/layout.ts`, a dialog at the top right): a top section about the user and player: the name block and, signed in, "Anfragen prüfen" / "Abmelden" / "Konto löschen" (`online.js` fills `#account-who` and `#account-actions`), and on team pages "Name wählen" (only while no player is chosen), "Meine Statistik" and "Ich bin nicht <Name>" (`#menu-pick`, `#menu-stats`, `#menu-clear` in the ME script, between the two; changing the player means "Ich bin nicht …" first; the pick opens the "Wer bist Du?" list of the Spieler page, also reachable with `#wer-bist-du`; the Übersicht hint links to it; the hint box on the Spieler page is only shown while no player is chosen), "App installieren" and "App teilen" (each only where available), the dark-mode toggle, "Was ist neu?" and "Datenschutz", then a "Feedback / Ideen" section with a Signal link (`SIGNAL_URL`, username-based, no phone number) and a mailto link to `PRIVACY_CONTACT` (both in `src/config.ts`; Umami events `feedback-signal`, `feedback-mail` via `data-track` on the item). Items marked `data-menu-close` close the menu before their action runs (capture listener on the dialog); the theme and share items keep it open so their feedback is visible. Umami event `menu`.
- The footer shows the data timestamp and the git commit the site was built from (short hash linked to GitHub, commit date). Without git the build still works, just without the version.
- Club logos on the Spielbericht and Vorschau pages (`teamLogo` in `src/render/components.ts`): the scrape lists the clubs of both regions (`CLUB_REGIONS` in `src/config.ts`, nuLiga `clubSearch`) into `data/clubs.json` and downloads each club's logo from its `clubInfoDisplay` page into `data/logos/<club id>.<ext>`, once per club (`logo: null` = the club has none; a failed download is retried next run and never fails the scrape). nuLiga serves an uploaded image only with the session cookie of the page that links it, so the logo request reuses it (`fetchBinary` in `src/fetch.ts`). A team is matched to its club by name: the longest club name the team name starts with, optionally followed by a numeral ("SV Weyhe IV" → SV Weyhe; `clubFor` in `src/logos.ts`). OT's own teams use `src/icons/club-logo.png`. The build copies the logos to `dist/logos/`; teams of clubs without a logo show none. The first scrape makes about two requests per club. The opponents' logos are their clubs' marks, taken from nuLiga's public club pages for display next to the team name.
- `data/` is not in git. The workflow keeps it in the GitHub Actions cache between runs. If the cache is evicted, the next run simply fetches all Spielberichte again.

## Test stages

Every pushed branch (except Dependabot's) gets its own test stage at `https://achimgrimm.github.io/badminton-results/stage/<branch>/`. The branch name is lowercased and other characters become `-`, so `feature/Lineup` is served at `stage/feature-lineup/`. `main` is the live site.

- Pushing or deleting a branch runs `.github/workflows/stage.yml`, which starts the main workflow on `main` (only `main` may deploy to GitHub Pages). So a stage appears a few minutes after the push and disappears when the branch is deleted.
- A stage is built with `STAGE=<branch>`. It shows a "Testversion" banner, isn't indexed or counted by Umami, installs as a separate app ("OT Test <stage>"), and prefixes its localStorage keys with `stage-<stage>-`, so testing never touches the live app's data. The live service worker ignores `stage/`.
- `mise run release`, run on the branch, releases it. It checks that the branch is pushed and that its stage already shows that commit, fast-forwards `main` to it and deletes the branch in one atomic push. The push run on `main` deploys it live and already drops the stage, so `stage.yml` skips its own run for that delete. If `main` has moved on, rebase, push and test the stage again.
- Local preview of a stage next to live: `npm run build && STAGE=my-branch npm run build && npm run serve`, then open `/stage/my-branch/`. A live build clears `dist/`, so build live first.

## Release notes

Tell users about new features with a file in `release-notes/`, named `YYYY-MM-DD-<slug>.md` (lowercase, digits, dashes):

```md
# Short title

What's new, in Markdown: paragraphs, lists, **bold**, [links](https://…).
```

The build (`src/releases.ts`, using `marked`) embeds the three newest notes in every page. On their next visit to a team page, users who already used the app see the notes newer than the last one they closed (localStorage `releaseSeen`); after a new-results pop-up, if there is one. New users skip the existing notes. The menu item "Was ist neu?" shows them anytime. A bad file name or a missing `# ` title fails the build. Umami event: `release-notes` (`via`: `auto` or `menu`).

## New season / other club

Teams are discovered from the club page, so a new season only needs `SEASON_LABEL` in `src/config.ts`. For another club, change `CLUB` (nuLiga club ID), `CLUB_NAME`, `CLUB_PREFIX` (the team name used in the leagues), `POOLS` (which roster age classes belong to which team label) and replace `src/icons/club-logo.png`. Then delete `data/` and run the scrape again.

The club logo in the header is TSV Osterholz-Tenever's; it is used with the user's OK (the other clubs' logos on the match pages come from nuLiga, see above) and the site stays labelled "Inoffizielle Ansicht".
